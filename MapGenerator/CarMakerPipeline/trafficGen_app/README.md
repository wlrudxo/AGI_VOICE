# TrafficGen App

TrafficGen App is a local desktop utility for inspecting and planning traffic
routes on roads generated by `roadGen_app`.

The app focuses on the important hard part: reading the actual SUMO lane
connections from `.net.xml` and building routes at lane level.

## Run

```powershell
cd <repo>\MapGenerator\CarMakerPipeline\trafficGen_app
python desktop_app.py
```

You can also double-click `run_app.bat`.

The unified pipeline app can launch TrafficGen with paths already filled in.
The direct command form is:

```powershell
python desktop_app.py --folder "<RoadGenExport>" --rd5 "<RoadFile.rd5>" --project "<CarMakerProject>" --scenario "route_traffic"
```

## Input

Select a single export folder from `roadGen_app/exports`, for example:

```text
<repo>\MapGenerator\CarMakerPipeline\roadGen_app\exports\figure8_road_20260513_140659
```

The app expects:

- `graph.json` for the original roadGen graph, optional but useful.
- `*.net.xml` for actual SUMO lane and connection data.
- `*.xodr` for best-effort OpenDRIVE road/lane ID mapping.
- `edge.xml` and `node.xml`, optional helper files.

## What It Does

The app reads `.net.xml` connections like:

```xml
<connection from="E2" to="E5" fromLane="0" toLane="0" via=":C_14_0"/>
```

and plans a route as:

```text
E2_0 -> :C_14_0 -> E5_0
```

This avoids the ambiguity of saying only `E2 -> E5`.

The route planner now uses a distance-weighted shortest path. It first tries a
lane-consistent route through SUMO junction connections. If that is not
available and `Allow lane changes` is enabled, adjacent lanes on the same SUMO
edge are also connected in the route graph. This lets the app still plan routes
such as:

```text
E10_0 -> E10_1
```

For longer routes, put intermediate lane IDs or SUMO/RoadGen node IDs in
`Checkpoints`, separated by spaces, commas, or semicolons. The app plans the
shortest path for each segment:

```text
Start lane -> checkpoint 1 -> checkpoint 2 -> Goal lane
```

If a checkpoint is a node ID, the planner automatically chooses the best usable
lane connected to that node.

You can also select lanes directly from the visualization canvas. Set `Canvas
click` to `Start`, `Goal`, or `Checkpoint`, then click a lane in the road view.
The selected lane ID is written into the matching route-planner field. Canvas
colors are:

- orange: current planned route
- green: start lane
- red: goal lane
- purple: checkpoint lanes
- blue: currently selected lane

The road view behaves like a small map viewer:

- mouse wheel: zoom in/out around the cursor
- drag empty background: pan the map

## Output

`Save Traffic Plan` writes files under:

```text
trafficGen_app/exports/<road_package>_<timestamp>/
```

Files:

- `traffic_plan.json`: machine-readable route and vehicle plan.
- `route_report.md`: human-readable route report.

`Generate XOSC` writes the same route plan plus:

- `<scenario>.xosc`
- a copied `.xodr`
- `Catalogs/Trajectory/TrajectoryCatalog.xosc`
- `run_osc2cm.ps1`
- `OSC2CM_README.md`

The XOSC uses two layers:

- `LanePosition` and `AssignRouteAction` from OpenDRIVE road/lane IDs.
- `FollowTrajectoryAction` from the actual SUMO lane shapes.

In CarMaker 15.0.1, `osc2cm` currently converts the trajectory layer into
`Traffic.*.Man.*.FollowTraj` entries. This is useful because it does not require
manual CarMaker route creation.

## Current Limit

CarMaker's converter may still print road API warnings for some junction links.
The generated TestRun should be inspected in CarMaker to verify that the vehicle
starts on the intended lane and follows the expected trajectory. This method does
not rely on CarMaker `Route ObjId`; it uses OpenSCENARIO trajectory conversion.

## RD5 Mapping Experiment

The app can also inspect a CarMaker `.rd5` road file and map the currently
planned SUMO/XODR route to CarMaker `LanePath` IDs.

Use:

```text
Browse RD5
Analyze Current Route Against RD5
Write Route Into RD5 Copy
```

The analyzer reads:

- `Link.*.Tag = odrRoadId:<id>`
- `Junction.*.Link.*.Tag = odrRoadId:<id>`
- `Link.*.LaneSection.*.LaneR/L.*.ID`
- `Junction.*.Link.*.LaneSection.*.LaneR/L.*.ID`
- `LanePath.* = <lanePathId> <laneObjectId> ...`
- existing `Route.*` blocks

Then it maps:

```text
XODR road/lane -> RD5 Link/Lane object -> RD5 LanePath ID
```

The current sample result maps both external lanes and junction-internal
connector lanes when the imported RD5 keeps `odrRoadId` tags on
`Junction.*.Link.*` entries.

`Write Route Into RD5 Copy` creates a new `.rd5` file under `exports/` and adds
a CarMaker route object:

```text
Route.N.ID = ...
Route.N.Name = ...
Route.N.DrvPath.ID = ...
Route.N.DrvPath:
    <LanePath ID>
    <ConPath ID, when a lane change is needed>
    <LanePath ID>
```

For same-road lane changes, the writer reuses an existing `ConPath.*` if the RD5
already contains one. Otherwise it creates a new connector path and inserts it
between the source and target `LanePath` IDs.

Lane changes are treated as relatively expensive planner transitions, not
near-free shortcuts. This keeps the planner from changing lanes immediately at
the route start when a longer lane-consistent road path exists. When a same-link
lane change is still required, the RD5 writer creates a non-zero-length
`ConPath` window on that link; if there are multiple lane changes on the same
link, those windows are spaced along the link instead of sharing the same `s`
coordinate. Generated lane-change connector widths are left as `-1` so CarMaker
uses the source/target `LanePath` widths, matching the common pattern in IPG's
example RD5 files.

Same-edge-only lane changes such as `E10_0 -> E10_1` are intentionally blocked
at RD5/TestRun export time. They can be planned and visualized in the app, but
CarMaker can place the vehicle off-road when a route consists only of an
in-link lane-change connector. Use start/goal lanes on different edges, or add a
checkpoint/goal beyond the lane-change edge.

This deliberately writes only the road-level `Route`/`DrvPath`. Ego vehicle
assignment and traffic object generation are separate CarMaker/TestRun steps:

- Ego vehicles usually reference the selected road route through the TestRun /
  driver manager setup.
- Traffic vehicles use `Traffic.*` entries or OpenSCENARIO conversion and may
  reference the route object differently.

Keeping route creation separate avoids mixing the RD5 road file with scenario
traffic state.

## CarMaker TestRun Generation

After a route has been planned, the app can now generate a CarMaker TestRun that
places the ego vehicle and traffic vehicles on a route ObjId.

Typical flow:

1. Plan a lane route.
2. For ego, click `Use Current` in the `Ego route` row.
3. Optional: plan another lane route and add traffic vehicles on that current route.
   For traffic cars, `Motion` selects how CarMaker drives the actor:
   `IPG Driver (AutoDriver)` writes `Traffic.<i>.AutoDriver.FName` and
   `Traffic.<i>.Man.0.LongStep.0.Dyn = auto <speed>`, while
   `Scripted constant speed` writes a simple
   `VelTransition <speed> linear` maneuver with no traffic AutoDriver template.
4. Optional: use `Random Pedestrians` to add walking pedestrians. Click one
   lane in the map, then click `Add Pedestrians On Selected Lane`; the app
   creates a short pedestrian route on that lane and scatters pedestrians along
   it. `Density persons/km` controls how many pedestrians are placed from that
   lane length. Start `s`, walking speed, lateral offset, and direction are
   randomized per pedestrian. Keep the offset range negative and outside the
   driving lane, for example `-2.3 .. -1.8`, so walkers stay near the visual
   sidewalk and do not disturb vehicle motion. The model and direction can also
   be fixed or set to `Random`.
5. Select the base or route-enabled RD5.
6. Set `TestRun name`.
7. Click `Generate TestRun`.

If the selected RD5 does not already contain a `Route.*` block for the current
route name, `Generate TestRun` first writes a route-enabled RD5 copy under the
selected CarMaker project:

```text
<CarMakerProject>/Data/Road/
```

The generated TestRun is written directly to:

```text
<CarMakerProject>/Data/TestRun/
```

The `TestRun name` field is the saved file name under `Data/TestRun`.

The default project path is:

```text
C:\CM_Projects\MapGen_TEST
```

`Generate + Run 5x + IPGMovie` generates the TestRun, then starts a CMAPI
interactive runner. The runner loads the TestRun, starts CarMaker, attaches
IPGMovie, waits briefly for the movie window to become ready, and requests
realtime factor `5.0`. The app does not show a blocking confirmation dialog
after launching the runner, so the movie window can show the beginning of the
run instead of jumping ahead while a modal dialog is open.
After the simulation reaches the finished state, the runner keeps
CarMaker/IPGMovie open so the final scene can be inspected or replayed. Close
the CarMaker/IPGMovie windows when you want the background runner process to
exit.

The runner writes its log under:

```text
<CarMakerProject>/Data/Config/
```

CarMaker 15.0.1 ships CMAPI/APO wheels for Python 3.9 through 3.13. Python 3.14
cannot load the bundled `apoc` wheel. If the app cannot find a compatible
interpreter, install Python 3.13 or 3.12, or set `CARMAKER_CMAPI_PYTHON` to that
`python.exe`.

The generated TestRun keeps ego and traffic separate:

- Ego car: `Vehicle.Routing.*`, `Vehicle.StartPos.*`, `DrivMan.*`
- Traffic cars: `Traffic.N`, `Traffic.<index>.Routing.*`,
  `Traffic.<index>.StartPos.*`, `Traffic.<index>.Man.*`.
  In `IPG Driver (AutoDriver)` mode, traffic cars use the selected CarMaker
  traffic driver template, for example `Car_Generic_Normal` or `Car_HDM_Normal`,
  and an `auto <speed>` long maneuver. In `Scripted constant speed` mode, the
  AutoDriver field is left empty and the car follows a fixed speed transition.
- Pedestrians: also `Traffic.N` entries, but with `2_People/...` templates and
  a pedestrian-style `VelTransition <walking speed> constAcc` maneuver. Their
  long/lat step limits use route distance (`s`), matching the CarMaker
  pedestrian examples. Random sidewalk pedestrians use `DetectMask = 0 0` so
  they are visible in IPGMovie but do not cause the default CarMaker driver to
  brake or stop.

No traffic actor is generated by default. Traffic cars and pedestrians are
written only when they have been added to the app's `Vehicles` list.

Ego and traffic cars may use different routes. The app writes any missing
CarMaker `Route.*` blocks into the project RD5, then references the correct
route ObjId from each `Vehicle.*` or `Traffic.*` block.

Clicking a row in the `Vehicles` list also switches the visualization to that
actor's route. This is only a display mode: the route planner's current route
is not overwritten. Selecting a new start lane, goal lane, or checkpoint from
the planner switches the visualization back to planner mode.

For route start placement, CarMaker uses:

```text
StartPos = <route s forward> <lateral offset>
```

So `Route s forward m` moves the vehicle along the route direction. `Lateral
offset m` moves it perpendicular to the route.

The TestRun references the route ObjId written into the RD5, so the RD5 copy
and TestRun must be used together inside the same CarMaker project.
