# CarMaker LLM Scenario Generation Skill Research

Created: 2026-05-12

## Goal

Build an LLM-assisted workflow for generating complete CarMaker scenarios.

Here "scenario" means the full simulation setup:

- map / road network
- ego vehicle initial position and route / trajectory
- other vehicles and pedestrians
- initial positions for all actors
- movement trajectories, speeds, timing, and trigger conditions
- CarMaker-loadable outputs that can be tested in `E:\CarMakerProject\AGI`

The previous chain was:

```text
LLM -> OpenDRIVE -> SUMO conversion -> CarMaker conversion
```

That is too indirect. The better target is:

```text
LLM structured scenario spec
  -> OpenSCENARIO .xosc + OpenDRIVE .xodr
  -> CarMaker osc2cm converter
  -> CarMaker TestRun / Road / TrafficTemplate files
```

For existing roads already in CarMaker, an even faster CarMaker-native path is:

```text
LLM structured scenario spec
  -> clone/edit a known CarMaker TestRun InfoFile
  -> modify Road.FName, Vehicle.*, DrivMan.*, Traffic.*
```

The first production skill should support both, but use OpenSCENARIO/OpenDRIVE as the primary interchange format because it directly represents full scenarios and CarMaker 15 includes a converter.

`osc2cm.exe --help` confirms:

- converts OpenSCENARIO v1.x to CarMaker TestRun for CarMaker 15.0.x
- requires `--cmprojpath` and `--oscfname`
- can validate OpenSCENARIO with `--validate`
- supports OpenSCENARIO validation versions `100`, `110`, `120`
- can select Ego with `--egoname`
- can select an ego vehicle InfoFile with `--egoinf`
- can auto-select traffic template files with `--trfmobj`
- can convert `FollowTrajectoryAction` polylines to CarMaker spline trajectories with `--interpolate`

Minimal command pattern:

```powershell
& "C:\IPG\carmaker\win64-15.0.1\bin\osc2cm.exe" `
  --cmprojpath "E:\CarMakerProject\AGI" `
  --oscfname "Data\OpenSCENARIO\pedestrian_crossing.xosc" `
  --egoname "Ego" `
  --egoinf "DemoCar_AEB_TEST" `
  --trfmobj `
  --interpolate `
  --validate `
  --oscversion 120 `
  --trfname "LLM_Test\pedestrian_crossing_from_llm"
```

Notes:

- `--oscfname` is relative to the CarMaker project path when relative.
- The generated TestRun should land under `Data/TestRun/...`.
- Use a subfolder-like name such as `LLM_Test/foo` only if CarMaker accepts it; otherwise create/copy into `Data/TestRun/LLM_Test/` after conversion.

## Web Research Summary

ASAM OpenDRIVE:

- OpenDRIVE describes static road networks for driving simulation.
- It covers roads, lanes, junctions, signals, objects, road geometry, and lane structure.
- It explicitly does not define dynamic content such as traffic participants and moving objects.
- Current ASAM page lists OpenDRIVE 1.8.1, but CarMaker converter compatibility should be checked against CarMaker 15's supported subset.

ASAM OpenSCENARIO XML:

- OpenSCENARIO XML describes dynamic scenario content.
- It covers synchronized maneuvers involving vehicles, pedestrians, and other traffic participants.
- It includes initial states, actions, triggers, routes, and trajectories.
- It is intended to be used with OpenDRIVE for the static road network.

IPG / CarMaker:

- IPG states CarMaker supports OpenSCENARIO and OpenDRIVE and provides a converter for OpenSCENARIO 1.x data.
- CarMaker 12 introduced the OpenSCENARIO Converter as an add-on and mentions direct input/simulation of scenarios defined in OpenSCENARIO.
- CarMaker 13 notes OpenSCENARIO Converter support for OpenSCENARIO 1.0, 1.1, and 1.2.
- Forum notes indicate import option choice matters: importing `.xodr` through the wrong menu can produce syntax errors.
- Forum notes also warn that some OpenSCENARIO/OpenDRIVE details such as elevation or decorative assets can be limited depending on version/settings.

Python libraries:

- `scenariogeneration` can generate OpenSCENARIO `.xosc` and OpenDRIVE `.xodr` from Python.
- It is not an official ASAM implementation.
- It can be useful as a writer library, but the final authority must be CarMaker's `osc2cm` validation and import behavior.
- `esmini` can play OpenSCENARIO XML and uses OpenDRIVE road networks. It is useful for quick non-CarMaker sanity checks, but passing esmini does not prove CarMaker compatibility.

## Recommended Skill Architecture

### 1. User intent to scenario IR

The skill should first ask the LLM to output a strict intermediate representation, not raw `.xosc` or native TestRun text.

Proposed IR:

```yaml
scenario:
  id: pedestrian_crossing_minimal_001
  description: Ego approaches a stopped bus; pedestrian crosses from right to left.
  road:
    mode: generated_opendrive
    kind: straight
    length_m: 250
    lanes:
      left: 0
      right: 2
      width_m: 3.5
    speed_limit_kmh: 50
  ego:
    name: Ego
    vehicle_infofile: DemoCar_AEB_TEST
    start:
      road_id: "0"
      lane_id: -1
      s_m: 10
      offset_m: 0
    behavior:
      type: speed_hold
      speed_mps: 13.89
  actors:
    - name: Pedestrian1
      type: pedestrian
      template_hint: 2_People/Pedestrian_Male_Casual_01_IPG
      start:
        road_id: "0"
        lane_id: -2
        s_m: 60
        offset_m: 5
      behavior:
        type: follow_trajectory
        trigger:
          type: ego_relative_distance
          value_m: 30
          rule: lessThan
        trajectory:
          coordinate: lane_position
          vertices:
            - {time_s: 0.0, road_id: "0", lane_id: -2, s_m: 60, offset_m: 5}
            - {time_s: 3.0, road_id: "0", lane_id: -1, s_m: 60, offset_m: 0}
            - {time_s: 6.0, road_id: "0", lane_id: 1, s_m: 60, offset_m: -5}
```

Why IR first:

- It lets the LLM reason in scenario terms.
- It can be validated before file generation.
- It can emit either OpenSCENARIO/OpenDRIVE or native CarMaker TestRun.
- It prevents accidental generation of CarMaker route ids that only exist in a different road file.

### 2. IR validation

Before emitting files, validate:

- every actor has unique name
- ego exists
- road ids / lane ids used by positions exist
- `s_m` is within road length
- pedestrian speed and vehicle speed are reasonable
- triggers refer to existing entities
- trajectory time is monotonic
- no actor starts inside another actor's bounding box
- generated OpenDRIVE lane ids match OpenSCENARIO `LanePosition` lane ids

### 3. File generation backends

Backend A: OpenSCENARIO/OpenDRIVE

- Generate `.xodr` for static map.
- Generate `.xosc` for entities, initial positions, speed actions, routes/trajectories, and triggers.
- Run CarMaker `osc2cm.exe --validate --interpolate --trfmobj --egoname Ego`.
- Inspect generated TestRun and TrafficTemplate outputs.

Backend B: Native CarMaker TestRun

- Only use when road is an existing `.rd5` with known route object ids.
- Clone a known TestRun such as `AEB_BusStop_collisiion_for_LLM`.
- Rewrite only:
  - `Description`
  - `Vehicle`
  - `Road.FName`
  - `Vehicle.Routing.*`
  - `Vehicle.StartPos.*`
  - `DrivMan.*`
  - `Traffic.*`
  - `Traffic.N`
- Do not attempt native `.rd5` generation in the first slice.

Backend C: IPGRoadAPI

- Keep as a later path.
- It is powerful but C/API-heavy and more brittle for an LLM skill than OpenDRIVE generation.
- Use it only if OpenDRIVE import/conversion cannot represent a needed map feature.

## Why Not SUMO First

SUMO is useful for traffic simulation, but it adds a third semantics layer:

```text
OpenDRIVE/SUMO network semantics
  -> SUMO edge/lane routes
  -> CarMaker road/routes/traffic semantics
```

For full CarMaker scenarios, SUMO is not the simplest source of truth. The scenario already needs CarMaker-compatible road ids, lane ids, actor templates, trigger semantics, and trajectory conversion. OpenSCENARIO/OpenDRIVE maps more directly to CarMaker's converter and to ASAM's split between static road and dynamic actors.

## Current Recommendation

Build the first skill around a strict YAML/JSON IR and an OpenSCENARIO/OpenDRIVE backend. Avoid SUMO entirely for the first slice.

Use native CarMaker TestRun editing only for scenarios on existing `.rd5` roads where route object ids are known. This gives a fast path for modifying existing AGI scenarios, but it is not the best path for generating new maps.

The first useful milestone is not "generate every scenario type." It is:

```text
natural language prompt
  -> validated IR
  -> simple .xodr + .xosc
  -> osc2cm converted TestRun
  -> CarMaker opens and runs it
```
